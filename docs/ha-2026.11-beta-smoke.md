# Home Assistant 2026.11 beta smoke test — DKN Cloud for HASS

**Candidate:** `0.5.0a4` (alpha); **test platform:** HA `2026.11.0b1` or later beta.
This is an optional validation procedure, not proof of compatibility.

## Before updating
1. Create a Home Assistant backup and note the currently installed integration
   version. Keep the previous package available for rollback.
2. Review the device's diagnostic capability bitmask and selected HVAC mode.
   Avoid including account email, token, MAC or device identifiers in reports.
3. Use an environment where a restart/reload is safe. Do not alter HVAC modes
   whose bitmask says they are unsupported.

## Installation and setup
1. Install the **prerelease** package from the integration's repository when
   published, enable the prerelease switch if required by Marketplace, then
   restart Home Assistant.
2. Verify the installed manifest reports **0.5.0a4** and that the config entry,
   entities, device/unique IDs, notifications and options load without errors.
3. In Marketplace confirm the integration appears under the existing catalog
   entry and uses the air-conditioning category.

## Device test: capability mask `11101000`
- Expected supported choices: **OFF, COOL, HEAT, FAN_ONLY (P2=3), DRY**.
  **HEAT_COOL/P2=4 is not selectable** even if an experimental opt-in was
  enabled by mistake. P2=6/7/8 are never mode-selector choices.
- The P0 guard also rejects forced mode-selection services when the corresponding
  capability bit is absent. If the capability mask is missing or malformed, only
  OFF is offered for selection; reported HVAC state must remain visible. Verify
  these cases using synthetic tests, **not by forcing unsupported hardware commands**.
- Confirm the device can **report** raw states separately from the selector.
  When raw mode=8, FAN_ONLY should display without a passive P2 write. A
  deliberate FAN_ONLY selection should send **P2=3** only if that capability
  is advertised. Never force a device into mode 8 to create this scenario.
- Exercise only modes previously known to work; check physical device response
  and HA state with timestamps. Do not send P2=4/6/7/8 to this device.
- Confirm temperature/fan controls in normal COOL and HEAT, and current
  power state from the official controller without exposing identifiers.

## Reliability and safety
1. Reload the config entry once and verify existing entities remain present.
2. Modify a safe option such as the polling interval and check that reload
   applies it; restore the intended setting.
3. Check logs for exceptions after a normal coordinator refresh. Do not
   expose raw tokens, user addresses or backend identifiers.
4. Record any discrepancy between physical state, backend snapshot and HA,
   but keep external-refresh investigations (#101/#102) separate.

## Pass criteria and rollback
- All eligible modes display correctly; unsupported commands are not offered.
- No unexpected P2 writes, changes to preset, duplicate entities or errors.
- If a fault appears, restore the backup or previous integration release,
  restart HA and attach a sanitized diagnostic (without secrets).
- This check does not validate P2=4, 6, 7 or 8 writes on other hardware.
