# Home Assistant 2026.11 stable compatibility and smoke checklist

**Status: automated compatibility gate passed; partial 0.6.0a1 owner
Marketplace/restart smoke passed, but fresh installation, legacy HACS migration,
full hardware acceptance and 0.6.0b1 beta acceptance remain pending.** Home Assistant 2026.11.0 was published on **2026-11-04**
and includes the built-in Marketplace. This checklist separates CI evidence
from real-device acceptance before claiming verified compatibility for
**DKN Cloud for Home Assistant**.

**Current declared minimum:** HA **2026.11.0**. The primary locked
development/test pair is `homeassistant==2026.11.1` and
`pytest-homeassistant==2026.11.1` on Python 3.14, as pinned in
`pyproject.toml` and `uv.lock`. The **separate, hash-locked minimum**
HA/official-pytest suite remains on **2026.11.0**. The old 2026.10.4/PHACC
lane is retired. Both suites, lint, HACS/hassfest, security and ZIP validation
must pass for the exact release-candidate SHA; check the
[main Actions runs](https://github.com/eXPerience83/DKNCloud-HASS/actions)
rather than treating historical runs as current sign-off.
Individual owner observations are not a substitute for full real-device and
fresh Marketplace/HACS migration acceptance. Published tags and ZIP assets
stay immutable.

## Gate 1 — reproducible HA 2026.11 tests

1. Install the matching stable official `pytest-homeassistant==2026.11.0`
   with `homeassistant==2026.11.0` using the independent hash-locked
   `.github/requirements/minimum-ha.txt` environment, as in the
   Minimum Home Assistant Compatibility workflow. The upstream PyPI
   publishing issue #190470 was fixed on 2026-11-05.
2. Verify Python, Home Assistant, the official pytest package, pytest and
   `.github/requirements/minimum-ha.txt` match the minimum-version
   requirements; the two harnesses must not coexist. The primary test
   environment uses the separately reviewed `uv.lock` (currently HA and
   official pytest-homeassistant 2026.11.1), while the independent minimum
   lane uses its own hashes at 2026.11.0. Both must pass separately.

3. Run the full integration suite, including config entry setup, unload,
   reload, migrations, device/entity registries, Climate, Switch, Sensor,
   API/auth/reauth, and their existing safety and coverage assertions.
   Review HA deprecations and any fixtures/imports affected by switching to
   the new official test package.
4. Run Ruff and packaging/hassfest/HACS validation. Review the
   new official harness and retain the agreed minimum of HA 2026.11.0.
5. Record results in [#121](https://github.com/eXPerience83/DKNCloud-HASS/issues/121).
   The retired PHACC suite is not evidence for HA 2026.11 compatibility.

## Gate 2 — native Marketplace and HACS migration

Use a backed-up HA **2026.11.0 or newer** installation where controlled HVAC
changes are safe. Record the exact HA version, DKN integration version and
commit; use pseudonyms, never credentials or hardware identifiers.

1. **Fresh Marketplace installation:** confirm this repository appears under
   the existing integration catalog and that its correct ZIP installs
   without errors. Add the DKN Cloud integration through
   **Settings > Devices & Services**, then check config flow, entry reload,
   device registry and unique entity IDs, platform setup, translations,
   diagnostics and default-disabled PII entities.
2. **HACS to Marketplace migration:** on a separate backed-up instance with
   the integration previously installed through HACS, upgrade HA and confirm
   that installed integration, options, config entries, update entities and
   unique IDs remain intact. Marketplace is built into 2026.11; installing
   the old HACS custom integration separately is not required.
3. **Release/packaging check:** verify tag and `manifest.version`, published
   prerelease status, `hacs.json.homeassistant` minimum, catalog category,
   `airzoneclouddaikin.zip` layout and expected files. This is acceptance
   of an already reviewed candidate, not permission to publish from the test.
4. **Inherited 0.6.0a1 migration check:** confirm existing config entries and
   entity IDs survive the removal of the user-facing `scan_interval` and
   `sleep_timeout_enabled` options when upgrading from pre-0.6.0 versions.
   Record the initial Sleep cleanup choice (default enabled) and test
   disabling it if needed. Retain a complete HA backup because downgrading
   the integration alone is not equivalent to restoring previous options.
5. **0.6.0b1 diagnostic acceptance:** on the installed beta, confirm exactly
   one enabled-by-default `Synchronization Mode` diagnostic sensor per
   device. Check unique ID stability, localized name/state labels, normal
   registry disable/enable behavior and no exposed PII. `push` must agree
   with sanitized `synchronization.devices.device_N.mode` when the
   subscription is healthy. Do not infer physical WServer connectivity or
   force a real socket outage solely to demonstrate `rest_fallback`.

## Gate 3 — real DKN hardware behavior

Use [the real-device evidence protocol](./real-device-validation.md).
Confirm the official DKN app and backend are healthy before comparisons.
Never force a mode that a device's capability bitmask does not advertise.

- Compare idle power, actual/target temperatures, supported HVAC modes,
  fan speed, presets and sensors with the official app.
- Exercise safe supported power on/off, COOL, HEAT, FAN_ONLY and DRY as
  applicable; confirm command acceptance **and actual device convergence**.
- Confirm `P1` Switch fallback when a sibling Climate entity is disabled,
  missing or restored as `unavailable`, if it can be tested safely.
  Existing synthetic regression tests do not prove this on HA 2026.11.
- Check supported bitmask behavior: P2=4 remains experimental and opt-in;
  telemetry aliases 6/7/8 are not normally user-selectable. Do not send
  unsupported commands to manufacture test data.
- Verify INFO-driven Pusher delivery at nominal cadence, state recovery
  through GET when Pusher is unavailable, and restart/reload behavior.
  For 0.6.0b1, compare the visible synchronization-mode diagnostic with
  sanitized transport diagnostics on the same device; a change to
  `rest_fallback` is **not** proof of physical WServer disconnection.
  A raw GET may show cached cloud data; distinguish incoming Pusher changes
  from optimistic HA state and physical equipment confirmation.
- Observe externally initiated wall-controller changes separately under
  #101 and authentication/reauthentication under #105. Do not turn a
  read-only acceptance observation into an unauthorized physical action.

## Sign-off and release decision

Mark each gate **passed, failed, or not tested** with its exact test environment.
Keep the [2026.11 Marketplace roadmap](https://github.com/eXPerience83/DKNCloud-HASS/issues/121)
open until tests and manual evidence genuinely exist.

Passing the HA 2026.11 official locked suite, HACS/hassfest checks or a successful
Marketplace download alone does **not** justify saying HA 2026.11 is verified.
The published `v0.6.0a1` has limited owner-reported Marketplace update and
post-restart healthy PUSH evidence on HA 2026.11.2 (#191). That evidence
does **not** establish a fresh install, legacy HACS migration, full entity
registry audit or comprehensive physical-command tests.

For the proposed `v0.6.0b1` beta, independently verify its **final reviewed
`main` SHA**, manifest/changelog version, all required CI lanes, ZIP layout
and SHA-256. Only then use [RELEASING.md](../RELEASING.md) to prepare and
inspect a **draft**; do not reuse `v0.6.0a1` or publish automatically.
Previously observed read-only INFO/Pusher delivery and two earlier physical
Sleep cycles do not certify the beta's installed package or all hardware.
The beta remains experimental; any public release requires a separate
manual approval, and #121/#191 stay open for unverified acceptance gates.
