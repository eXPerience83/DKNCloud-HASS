# Home Assistant 2026.11 stable compatibility and smoke checklist

**Status: pending; not a compatibility certification.** Home Assistant
2026.11.0 was published on **2026-11-04** and includes the built-in Marketplace.
This document describes the evidence required before claiming that
**DKN Cloud for Home Assistant** supports HA 2026.11 in a new release.

**Current declared minimum:** HA **2026.10.4** (keep unchanged until a
separately reviewed support-policy change). The locked CI test harness is
HA 2026.10.4 / PHACC 0.13.375 on Python 3.14.10; it is **not** a 2026.11 test.
The most recently published DKN alpha is **v0.5.0a4**, but it predates later
`main` fixes. A future alpha requires a **new** version and release review.
Do not alter published releases or their assets.

## Gate 1 — reproducible HA 2026.11 tests

1. Confirm that the official Home Assistant 2026.11 test harness is available.
   HA is replacing the third-party
   `pytest-homeassistant-custom-component` (PHACC) with its official
   `pytest-homeassistant` package. On **2026-11-05**, the stable 2026.11.0
   package was blocked by an [upstream PyPI publishing issue](https://github.com/home-assistant/core/issues/190470);
   verify the current upstream state before attempting the migration.
2. In a **disposable, isolated environment**, install the exact stable HA
   2026.11.x version with its matching official test harness. Record exact
   Python/HA/harness/pytest versions and dependency-resolution failures.
   Never let this experiment silently alter the repository's `uv.lock`,
   supported minimum or required CI.
3. Run the full integration suite, including config entry setup, unload,
   reload, migrations, device/entity registries, Climate, Switch, Sensor,
   API/auth/reauth, and their existing safety and coverage assertions.
   Review HA deprecations and any fixtures/imports affected by switching to
   the new official test package.
4. Run Ruff and packaging/hassfest/HACS validation against the candidate,
   then open a **separately reviewed** test-baseline migration PR. If the
   locked HA test baseline advances while HA 2026.10.4 remains supported,
   restore an **independently pinned minimum-HA test lane** before merging
   the new baseline. See [#109](https://github.com/eXPerience83/DKNCloud-HASS/issues/109).
5. Record results in [#121](https://github.com/eXPerience83/DKNCloud-HASS/issues/121).
   A pass on HA 2026.10.4 or a PHACC canary selecting 2026.10.4 does
   **not** fulfill this gate.

## Gate 2 — native Marketplace and HACS migration

Use a backed-up HA **2026.11.0 or newer** installation where controlled HVAC
changes are safe. Record the exact HA version, DKN integration version and
commit; use pseudonyms, never credentials or hardware identifiers.

1. **Fresh Marketplace installation:** confirm this repository appears under
   the existing integration catalog and that its correct ZIP installs
   without errors. Add the DKN Cloud integration through
   **Settings > Devices & Services**, then check config flow, entry reload,
   device registry and unique entity IDs, platform setup, translations,
   diagnostics and default-disabled PII entities.
2. **HACS to Marketplace migration:** on a separate backed-up instance with
   the integration previously installed through HACS, upgrade HA and confirm
   that installed integration, options, config entries, update entities and
   unique IDs remain intact. Marketplace is built into 2026.11; installing
   the old HACS custom integration separately is not required.
3. **Release/packaging check:** verify tag and `manifest.version`, published
   prerelease status, `hacs.json.homeassistant` minimum, catalog category,
   `airzoneclouddaikin.zip` layout and expected files. Do not publish a
   new alpha as part of this smoke test.

## Gate 3 — real DKN hardware behavior

Use [the real-device evidence protocol](./real-device-validation.md).
Confirm the official DKN app and backend are healthy before comparisons.
Never force a mode that a device's capability bitmask does not advertise.

- Compare idle power, actual/target temperatures, supported HVAC modes,
  fan speed, presets and sensors with the official app.
- Exercise safe supported power on/off, COOL, HEAT, FAN_ONLY and DRY as
  applicable; confirm command acceptance **and actual device convergence**.
- Confirm `P1` Switch fallback when a sibling Climate entity is disabled,
  missing or restored as `unavailable`, if it can be tested safely.
  Existing synthetic regression tests do not prove this on HA 2026.11.
- Check supported bitmask behavior: P2=4 remains experimental and opt-in;
  telemetry aliases 6/7/8 are not normally user-selectable. Do not send
  unsupported commands to manufacture test data.
- Verify reload, restart, polling/refresh after external app changes,
  coordinator recovery and error handling. Track unresolved stale refresh
  behavior separately in #101/#102 and account reauthentication in #105.

## Sign-off and release decision

Mark each gate **passed, failed, or not tested** with its exact test environment.
Keep the [2026.11 Marketplace roadmap](https://github.com/eXPerience83/DKNCloud-HASS/issues/121)
open until tests and manual evidence genuinely exist.

Passing the HA 2026.10.4 locked suite, HACS/hassfest checks or a successful
Marketplace download alone does **not** justify saying HA 2026.11 is verified.
Only after review of the evidence should a maintainer deliberately prepare a
**new** DKN alpha draft using [RELEASING.md](../RELEASING.md). Publication
remains a separate, manual decision; no automatic release or support-floor
increase is permitted.
